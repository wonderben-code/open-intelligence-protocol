# CLAUDE.md

This repository is the **Open Intelligence Protocol (OIP)**: a free, open protocol stack for coordination between minds, meaning people, AI agents, collectives and institutions. It holds the papers, the normative specifications, the test vectors and, from M0 onwards, the v1 reference implementation. The project owner is Ekram Alam, who goes by Eks.

## Start every session here

1. Read [PROGRESS.md](PROGRESS.md) to see where things stand and what comes next.
2. Read [BUILD.md](BUILD.md), the plan. Work on the first milestone that is not done, in order.
3. For anything about protocol behaviour, read the relevant part of [spec/](spec/) before writing code.

## Sources of truth

- **`spec/*.md` is normative.** The papers explain the design. If a paper and a spec disagree, the spec wins and the paper gets fixed.
- **`spec/test-vectors/vectors.json`** holds golden values generated by an independent Python implementation, `oip_vectors.py`. Reproduce them byte for byte.
- **If the code reveals a gap or a mistake in the spec**, fix it properly, in one change:
  - the spec text;
  - an entry in [spec/CHANGELOG.md](spec/CHANGELOG.md);
  - the Python generator and the vectors;
  - the technical paper.

  Never let the code diverge from the spec silently. Record formats change only through a spec revision.

## Commands

Node.js 24 is at `/opt/node24/bin` in the cloud container; put it first on `PATH`. pnpm switches itself to the version pinned in `package.json`.

```
pnpm install                         # dependencies
pnpm build | test | lint | typecheck
pnpm test:vectors                    # the golden vectors, by case kind
pnpm test:differential               # against the Python checker (needs python3 with `cryptography`)
pnpm spec:coverage                   # which spec clauses have tests; writes docs/conformance/coverage.md
pnpm schemas                         # regenerate spec/schemas and the compiled validators
pnpm spec:clauses                    # regenerate spec/clauses.json after a spec change
pnpm generated:check                 # both of the above are current
pnpm api                             # build, and update the API reports (packages/*/etc)
pnpm newcomer                        # the five-minute promise: follows packages/cli/README.md, timed
pnpm mcp:inspector                   # the MCP server under the MCP Inspector (fetches it with npx)
pnpm bench                           # performance budgets (BUILD.md 3.8)
pnpm mutation                        # mutation testing with Stryker (slow; CI runs it weekly)
pnpm run docs                        # API reference (`pnpm docs` is pnpm's own command)
```

Before pushing, run `pnpm run ci`. It is the script the main CI job runs (`scripts/ci.ts`): every check, in order, from a clean build.

Also:

```
python3 spec/test-vectors/oip_vectors.py --check   # needs the `cryptography` package
cd papers/build && npm install && python3 build.py # rebuild the papers' PDFs
```

## Rules that are never broken

- **Cryptography.** Never implement a cryptographic primitive. Ed25519 verification follows core 4.4 exactly: `S < L`, canonical encodings, and `A` and `R` of order exactly L.
- **Numbers.** No floats in records. Decimals are strings, with exact arithmetic.
- **Validate, verify, then use.** Everything from outside is untrusted until it has passed its schema, the core rules and verification.
- **Secrets.** Never log, print, return or put into a model's context a private key or any other secret.
- **Purity.** The pure packages (`schema`, `core`, `identity`, `delegation`, `web`, `net`) do no I/O and never read the clock. The current time and the evidence are parameters.
- **Traceability.** Every requirement has a test that cites its clause, for example `clause("L1 6.4")`.
- **Dependencies.** Keep them few and audited, with each one justified in an ADR (`docs/adr/`).

## Git and provenance

- Every push to `main` is timestamped on the Bitcoin blockchain, and a bot then commits the proof to `timestamps/`.
  - Fetch before you push.
  - Merge, never rebase, anything already on `main`.
  - Never force-push `main`.
- Work on one branch per milestone (for example `m2-identity`) and commit small and often. Open a PR to `main` when the milestone's acceptance criteria pass and CI is green, and merge it with a merge commit.
- Push at least once at the end of every session, so no work is lost to a usage limit.
- Commit messages: an imperative summary line, and a body that says why. Add the attribution trailers your harness asks for.

## Quality gate for every milestone

A milestone is done when:

- its acceptance criteria in BUILD.md pass in CI, with the coverage and mutation thresholds met;
- its documentation is written and every changed package has a changeset;
- a fresh review agent, given only the repository, the spec and the diff, has checked it for spec conformance, security and test quality;
- every finding is fixed (or logged as an issue), and the review is saved as `reviews/build/M<n>-<name>.md`;
- [PROGRESS.md](PROGRESS.md) is updated.

## Writing

Write docs in British English (organise, licence as a noun), plainly and precisely. Use short sentences, define each term once, and use no hype in specs or docs. Code comments say why, not what.

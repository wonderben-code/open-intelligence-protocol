# ADR-0011: HPKE as adopted in `@oip/core`

**Status:** Accepted, 18 November 2026 (M4). It records what [ADR-0002](0002-cryptography-libraries.md) asked M4 to check, and what M4 found.

## Context

A `Sealed` record is a signed packet encrypted to one of its recipient's agreement keys with HPKE (RFC 9180): base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256 and ChaCha20-Poly1305 (Layer 1, 12.6). OIP never implements a cryptographic primitive, and HPKE's key schedule is one. ADR-0002 chose `@hpke/core`, `@hpke/dhkem-x25519` and `@hpke/chacha20poly1305` for it, and said that each adoption checks the facts again.

## What was checked

### Versions, and where the code comes from

| Library                  | Installed | Depends on     |
| ------------------------ | --------- | -------------- |
| `@hpke/core`             | 1.10.1    | `@hpke/common` |
| `@hpke/dhkem-x25519`     | 1.8.1     | `@hpke/common` |
| `@hpke/chacha20poly1305` | 1.8.1     | `@hpke/common` |
| `@hpke/common`           | 1.13.0    | none           |

All four are MIT, by one author. None reports an independent audit.

The curve and the cipher are not the audited `@noble` packages that `@oip/core` already depends on. They are copies: `@hpke/common` carries X25519 "based on noble-curves" at a commit it names, with a timing hardening of its own, and `@hpke/chacha20poly1305` carries ChaCha20-Poly1305 "based on noble-ciphers" at a commit it names. So the audits of the `@noble` packages are evidence about the design these copies come from, and not about the copies. HKDF-SHA256 is the platform's (WebCrypto), which is why the functions are asynchronous.

The tests below are what OIP relies on.

### Against published vectors

- **RFC 9180, Appendix A.2.1** (the suite OIP uses, base mode). With the RFC's `ikmE`, recipient key, `info`, plaintext and associated data, `hpkeSeal` gives the RFC's encapsulated key and its first ciphertext, byte for byte. `hpkeOpen` opens the RFC's ciphertext with the RFC's recipient key.
- **Against the audited curve library.** The public key the RFC gives for its recipient is the one `@noble/curves` derives from the private key, and `x25519PublicKey` is that derivation.
- **Round trips.** Generated messages, keys and associated data open to what was sealed.

### What the library does with what must be refused

- **A recipient key of small order.** RFC 9180, 7.1.4 requires a sender to check that the shared secret is not all zero: with such a key every sender would share the same secret. The library refuses each of the seven encodings of a point of small order, as `@noble/curves` does. The tests seal to each and require a refusal, and open with each as the encapsulated key and require a refusal.
- **Anything changed.** A ciphertext with one bit changed, a ciphertext cut short, another `info`, other associated data, another key and an encapsulated key of another length each fail to open.

## Decision

1. **HPKE goes through `@oip/core`**, like every other use of cryptography. `hpkeSeal` and `hpkeOpen` fix the suite. `@oip/net` builds the `Sealed` record on them and imports no cryptography itself.
2. **One message for each encapsulation.** OIP seals each packet on its own, so the single-shot form of RFC 9180, 6.1 is all that is exposed.
3. **The sender's randomness is a parameter**: 32 bytes, from which the library derives the ephemeral key (`ikmE` in the RFC). The pure packages draw no randomness. The cost is an argument that must never be used twice for one recipient, which the documentation of `hpkeSeal` and of `sealPacket` says in words. The packages that hold keys (M6) draw it from the platform and are the only callers.
4. **Nothing that arrives makes `hpkeOpen` throw.** It answers with the plaintext or with `undefined`. `hpkeSeal` answers with `undefined` for a recipient key that cannot be sealed to. The library's own error is never passed on: it could speak of key material.
5. **Arguments are copied before the first wait**, so that what is sealed is what was given, whatever the caller does to its bytes meanwhile.
6. **A key the library has read is opaque to `@oip/core`.** The library's declarations name the platform's `CryptoKey`, which not every platform the package runs on declares. `@oip/core` declares the four functions it calls and hands the keys back as it got them.

## Alternatives

- **Building HPKE from the `@noble` packages.** Each primitive would be audited, and the construction would be ours. That is the thing this project does not do.
- **WebCrypto alone.** Node.js 24, which the build runs on, has key encapsulation in WebCrypto and no HPKE: `generateKey` with the name `HPKE` is refused as an unrecognised algorithm.
- **Taking the randomness inside `@oip/core`.** It would make misuse harder and the package impure. The few callers are our own.

## Consequences

- Sealing and opening are asynchronous. Verifying a packet stays synchronous: only the opening of a `Sealed` record waits.
- OIP depends on one more maintainer, for code that no third party has audited. The mitigations are the pinned versions, the seven-day release delay ([ADR-0001](0001-tooling.md)), the RFC's vectors in our own tests, and the narrow use: one suite, one mode, one message for each key.
- The Python checker does not seal or open. A second implementation of sealing, to test against, is owed to a later milestone.
- If an audited HPKE library appears, or the `@noble` family gains one, replacing these is a change to `packages/core/src/hpke.ts` and to this record.

# ADR-0016: Ed25519 by OpenSSL in the services

**Status:** Accepted, 20 November 2026 (M5).

## Context

A signature costs the portable implementation about 2 ms, almost all of it three scalar multiplications in JavaScript big-integer arithmetic ([ADR-0006](0006-performance-budgets.md)). The first two budgets of [BUILD.md](../../BUILD.md), Section 3.8, stand at twice what was asked: 4 ms for a record with two proofs against 2 ms, and 2 s for a log of a thousand events against 1 s. ADR-0006 gave the portable implementation budgets of its own and kept the starting budgets as the targets for the services, to be met with a native Ed25519 in M5. It set two conditions: core 4.4 is not weakened, and the engine is adopted only with the tests of `@oip/core` run against it unchanged and with differential runs against the portable implementation.

[ADR-0015](0015-server-budgets.md) made a signature that verified cost nothing the second time. What is left is the first time: a log a service has not seen is verified in one piece, and the service answers nothing else meanwhile.

Node.js has OpenSSL. Its Ed25519 checks the equation of RFC 8032, 5.1.7 without the cofactor: `S` is below L, and the encoding of `[S]B - [k]A` is `R`, byte for byte. It does not check that `A` has order L, and it accepts signatures by some keys with a small-order component.

## Decision

1. **`@oip/core` can be given an engine for the arithmetic of a signature** (`useEd25519Engine`). An engine answers one question: whether `S` is below L and `[S]B - [k]A` encodes as `R`.

2. **The rule stays core 4.4, and stays in `@oip/core`.** With an engine, `verifyEd25519` still checks for itself that `A` is the canonical encoding of a point of order L, as it always has, and that `R` is not the identity. Then it asks the engine. That is the rule exactly:

   - If `A` has order L, then `[S]B - [k]A` is in the subgroup of prime order. An `R` that is its encoding, byte for byte, is therefore canonical, and has order L unless it is the identity, which is refused. `S` is below L, and the equation holds. So what the engine accepts meets all four items of core 4.4.
   - The other way: if all four items hold, `A` and `R` have order L, so `[S]B - R - [k]A` is in the subgroup of prime order. The equation with the cofactor says that eight times it is the identity, and in that subgroup only the identity is. So the equation without the cofactor holds, `R` is the canonical encoding of `[S]B - [k]A`, and the engine accepts.

3. **An engine is tried before it is used**, on signatures whose answers are fixed in `@oip/core`: honest ones, one for another message, one whose `S` is not below L, and three whose `R` has a small-order component and which satisfy the equation with the cofactor. An engine that gives another answer for any of them, or throws, is refused. That catches an engine of another kind, such as one that multiplies by the cofactor or reduces `S` first. It is not a defence against code in the process that means harm: such code needs no engine.

4. **A process has one engine.** The same one given again changes nothing, another is refused, and there is no way in the package's interface to take one out.

5. **Only its `true` is a yes.** Any other answer is a no, and a throw is a no that is not remembered.

6. **The engine is OpenSSL, through `node:crypto`, and lives in `@oip/server`** (`nativeEd25519`, `useNativeEd25519`). The pure packages import nothing of Node.js, as before. Each service takes the engine when it starts. If the OpenSSL of a platform fails the trials, the service says so in its log and goes on with the portable library. The setting `ED25519` chooses `native` or `portable`, and `native` is the default.

7. **The portable library stays the reference.** Everything outside the services uses it: clients, browsers, the command line, the tests of the pure packages. Every budget of ADR-0006 is still measured and still gated.

## How it is tested

- **The tests of core 4.4 run three times, unchanged**: with the library, with an engine written out from RFC 8032 with the library's point arithmetic, and with OpenSSL. They are the RFC 8032 vectors, every crafted signature (an `S` that is not reduced, each non-canonical encoding, each small-order point as a key and as `R`, each mixed-order key and `R`), and the tests that the bytes verified are the bytes that were checked.
- **A differential test** makes signatures of ten kinds and compares the three, in `@oip/core`, and compares the library with the engine `@oip/server` ships, in `@oip/server`. `OIP_ED25519_RUNS` sets how many.
- **Wrong engines are refused**: one that always says yes, one that always says no, the library's own strict mode (which multiplies by the cofactor), one that reduces `S`, one that throws, and ones that answer with something that is not `true`.
- **The golden vectors, and the differential tests against the Python checker, run with the engine as well** (`OIP_ED25519=native`).

## Measurements

Machine: the cloud container of ADR-0006, four cores, Node.js 24.22 with OpenSSL 3.5. Each sample forgets the signatures that verified before it. The figures for the portable library in the second and third rows are those of ADR-0006.

| Operation                                             | The portable library | OpenSSL | Target of BUILD.md 3.8 |
| ----------------------------------------------------- | -------------------- | ------- | ---------------------- |
| One signature under core 4.4, the key seen before     | 1.9 ms               | 0.12 ms |                        |
| A record with two proofs, read from text and verified | 3.9 ms               | 0.4 ms  | 2 ms                   |
| An identity log of 1,000 events, verified end to end  | 1.8 s                | 0.25 s  | 1 s                    |

`packages/server/bench/verify.bench.ts` holds the services to the two targets, and holds OpenSSL to a fifth of the portable library's time for a signature: it measures at a sixteenth.

In one process, a log published to a resolver for the first time, by the number of its events, in milliseconds:

| Events | With the portable library | With OpenSSL | The same bundle again, with either |
| ------ | ------------------------- | ------------ | ---------------------------------- |
| 1      | 6.0                       | 2.7          | 2                                  |
| 2      | 9.1                       | 4.9          | 3 to 4                             |
| 12     | 39                        | 10.5         | 10 to 11                           |
| 100    | 276                       | 73           | 58 to 63                           |

With OpenSSL a new log costs little more than a known one. What is left is the reading and hashing of each event, and the order check of each key it brings, which `@oip/core` does itself and remembers.

The four budgets of the services under load are in ADR-0015, with and without OpenSSL: a published bundle goes from a 99th percentile of 27 ms to 18 ms, and a delivery over a WebSocket from 8 ms to 4 ms.

## Consequences

- A service checks a signature for the first time in a sixteenth of the time. The first two rows of BUILD.md 3.8 are met in the services.
- A new log is still verified in one piece. A thousand events now take a quarter of a second.
- Two things do the arithmetic, and they must agree for good. The trials at start-up, the three runs of the rule's tests and the differential tests are what holds them together, and the nightly workflow runs the differential test at length.
- An OpenSSL that changed what it accepts would fail a trial or a test before it changed a verdict: the trials are of the cases where engines differ.
- A verifier outside a service is no faster than before.

## Alternatives

- **WebAssembly.** One engine for every platform, the browser included. It would be a new dependency that does cryptography, to be chosen and audited as the libraries of ADR-0002 were, where OpenSSL is in the process already. The services do not need it. A client in a browser might: that is a later decision, and the hook is the same.
- **`crypto.subtle`.** It is OpenSSL underneath in Node.js, and asynchronous: every judge in the pure packages would have to become asynchronous to use it.
- **Assemble the check from faster point arithmetic.** ADR-0006, item 3: the verification equation is not put together here to make it cheaper.
- **No engine.** The five budgets of the services are met without one (ADR-0015). The first two rows are not, and a long log seen for the first time holds a service ten times longer.

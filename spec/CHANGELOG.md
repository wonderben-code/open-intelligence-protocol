# Specification changelog

## Since revision 2026-11-17 (not yet dated)

Changes adopted while the reference implementation is built. They stay under this heading until the maintainer dates the next revision ([GOVERNANCE.md](../GOVERNANCE.md)), which [BUILD.md](../BUILD.md) plans for the release candidate (M12). Each names its OEP.

**Core clarifications and limits ([OEP-0001](../oeps/oep-0001-core-clarifications.md), found while building `@oip/core` and in its two independent reviews).** No address, content ID or proof in the test vectors changes.

- **Depth (core 1.9, new).** Arrays and objects nest at most 64 deep, the record itself being depth 1. The specification set no limit, so two implementations could disagree about a deeply nested record, and one could be made to exhaust its stack. Layer 1, Section 19 lists the limit.
- **Containers are limited part by part (core 1.6, 1.9, 12).** For `Bundle`, `LogPage`, `FeedPage` and `DuplicityEvidence`, the limits on size and on depth apply to each record the container carries, counted from that record, and to the container without the members that hold those records. A container can therefore carry any record that is valid alone, and its own members are bounded too. Before, a container's own members had no size limit, and a record nesting 64 deep could not be carried at all.
- **Noncharacters (core 1.1).** A string in a record holds no noncharacter, as I-JSON (RFC 7493, Section 2.1) requires. core 1.1 named I-JSON and only two of its three rules.
- **Durations (core 1.5).** A duration string is at most 64 characters, as a decimal is.
- **Size counts proofs (core 1.6).** The 1 MiB limit is on the canonical form of the record with its `proof` member. The rules of core 1 apply to every entry of `proof`.
- **Proof entries are objects (core 5.1).** An entry of `proof` that is not a JSON object makes the record malformed. An entry that is an object but not a valid proof does not count, and does not make the record malformed.
- **Year 0000 (core 1.4).** Years run from `0000` to `9999` of the proleptic Gregorian calendar, as in RFC 3339, and year `0000` is a leap year. The Python checker rejected year `0000`; it now accepts it.
- **`"-0"` (core 1.3).** It is a decimal equal to `"0"`, and not an amount.
- **Key hashes (core 3.4).** A key hash matches the content-ID pattern of core 3.2. Both implementations already required it.
- **Positions (core 6.1).** A `seq` greater than 2⁵³−1 names no event.
- **Types that extensions define (core 7).** A record whose `type` this specification does not define lists the extension that defines it in `critical`. core 7 said "defined by this specification or by a critical extension"; this states what follows.
- **Extension names (core 8.1, 8.3).** A member of `ext` whose name is not a namespace makes the record malformed. A namespace repeated in `critical` counts once.
- **`kind` (Layer 1, 3.6).** A `kind` is not empty. Both implementations already required it.

**Test vectors.** `vectors.json` now holds 17 must-accept cases (5 in revision 2026-11-17), 80 negative cases (55) and 30 controls (11). Every value that was there is byte for byte what it was.

- A new kind of case, `json`, gives texts that a parser of the JSON profile must read (5 must-accept cases: integers however they are written, an integer written with 5,000 digits, escapes, the same member name in different objects, nesting 64 deep) and must refuse (12 negative cases: fractions, integers outside the safe range, an unpaired surrogate, noncharacters of each kind in a string and in a member name, nesting 65 deep, text that is not JSON). Duplicate member names are not among them, because core 1.1 says receivers SHOULD reject those.
- Cases of kind `record` now also stand among the must-accept cases and the controls. Seven must be accepted: a type an extension defines, year 0000, a rating of `-0`, a duration of 64 characters, nesting 64 deep, and a page and a `DuplicityEvidence` each carrying an event that nests 64 deep. Eleven must be rejected: a `proof` entry that is not an object, an extension name that is not a namespace, an unknown type with no critical extension or with no `created`, a duration of 65 characters, nesting 65 deep, and a record nesting 65 deep in each kind of container and in a container's own part.
- Two negative cases of kind `countsFor`: a signature whose `R` has a small-order component (core 4.4), and a key reference whose position is 2⁶⁴+1 (core 6.1).
- Nineteen controls, among them one for each signature that breaks core 4.4: the same record with an honest signature counts.
- The file itself holds no float, unpaired surrogate or noncharacter: such things are written as escapes inside the texts that test them.

**The Python checker** gained a parser for the profile, and applies core 1.1, 1.2, 1.6 and 1.9 to every record it judges, container by container, and core 1.1, 1.2 and 1.9 to every identity event. It checks the length and form of a packet's retention period (core 1.5). It reads a number of any length as text: before, Python's own limit of 4,300 digits made it reject an integer written at length. It compares a proof's `@context` with the record's in canonical form: before, it took `true` for `1` and a missing member for `null`. It rejects a `proof` entry that is not an object and an `ext` member whose name is not a namespace, as the specification requires.

**Identity clarifications ([OEP-0002](../oeps/oep-0002-identity-clarifications.md), found while building `@oip/identity`).** No address, content ID or proof in the test vectors changes.

- **A proof pinned to a `Retire` counts for nothing (Layer 1, 6.1, 6.4).** A `Retire` leaves a mind's keys in their sets, and the rule looked only at later events for a removal or a retirement. A proof that pinned the `Retire` itself was therefore by a valid key, and a retired mind's keys could go on signing. The Python checker accepted such a proof; it now rejects it.
- **Every event is a well-formed record (Layer 1, 4.8, new).** A log with an event that breaks Section 3, or core Sections 1, 5.1 and 7, does not verify, whoever signed the event. The Python checker verified a signed genesis with nine homes; it now applies the shape of Section 3 to every event.
- **HTTPS origins (Layer 1, 3.13, new).** `https://` and then a host and an optional port, written with ASCII letters, digits and `.`, `-`, `:`, `[`, `]` only. Section 3.6 and the `homes` of a `Location` refer to it. The schemas allowed any character but `/`, `?`, `#`, `@` and white space, which is not one set in every implementation.
- **Controllers and key entries have no other members (Layer 1, 3.4, 3.5).** Both implementations already required it.
- **`Fork` and `Retire` may carry the key sets (Layer 1, 3.8, 3.10)**, with the meaning they have in an `Update`. Section 4.5 already applied them to every event.
- **`recovery` is reserved as a member of the event itself (Layer 1, 3.12)**, and not inside another member.
- **A container or a `Sealed` record has no `created` (core 7).** A reader ignores one there, as it ignores any member it does not recognise.

Two independent reviews of `@oip/identity` found the rest. In the first six, both implementations gave the same answer, and it was not the one the text gives or needs.

- **A critical extension the verifier does not implement (core 8.3; Layer 1, 4.8).** An identity event that lists one is not treated as valid, so its log does not verify for that verifier; a record that lists one counts for nobody. Both implementations ignored `critical` here.
- **A duplicitous collective signs nothing from its first conflicting event on (Layer 1, 7.3, 9.5).** A record signed under a threshold pins no version of the collective, so the rule about versions did not reach it, and the collective went on signing with the members it had before its branches parted.
- **An event the verifier cannot judge holds its position (Layer 1, 7.3).** Both implementations dropped a branch that failed anywhere, so one junk event after the honest event made the other branch win. Now a verifier judges every event it holds at each position: an invalid event is no event, one that verifies carries the log on, and one that is undecided stops the log, whatever else is held at that position, since it may be the mind's own. What follows an event that lost its position is not judged. An event loses only to one with strictly earlier evidence: where two tie, a third seen later is a conflicting branch like them.
- **The earliest time `T` of Layer 1, 9.5 ranges over the collective's own events as well as the proofs.** A record is signed from the moment a change of membership completes its threshold. A `Hello` is never signed under a threshold: core 11 gives it to the author's own key.
- **A member's proof that names an `authority` does not count on an identity event (Layer 1, 6.4).**
- **core 9.3 and 9.6 apply to the proofs on an identity event (core 9.5; Layer 1, 6.4, 4.8).** A proof there dated more than 300 seconds after the evidence for the event does not count, and an event evaluated more than 300 seconds after its `expires` is invalid.
- **An event that fails is invalid or undecided (Layer 1, 4.9, new).** An event is invalid if the verifier can read it and what is wrong can be seen in the log alone: it is malformed, out of place, or carries proofs that no evidence and no member's log could make good. It is no event, and a copy ends before it. Every other event that fails is undecided (for want of evidence, of a member's log, of an extension, or of a later revision); it may be a removal, and the events before it are not taken as the log. A verifier keeps what it has been shown: every event of every copy, with every proof, judged when it is asked. A verifier that kept "what verified" of a log could otherwise go on counting a key that the next event removed.
- **The proofs of one event count together (Layer 1, 7.1).** The same event with another set of proofs is not duplicity; a verifier that holds it in two copies judges it with the proofs of both, wherever in a copy the event stands. Only a well-formed copy of the event counts for this. One whose `proof` is not what core 5.1 requires adds no proof and takes none away; it keeps its place, and what follows it in its copy is held. A value has a place in a copy if, apart from its `proof`, it is a JSON object within core Section 1, of at most 1 MiB: that is what its content ID covers, so nothing inside `proof` costs an event its place. Any other value is no event, and nothing after it in that copy is held; a copy that begins with one is a copy of no mind's log. A content ID does not cover `proof`, so without this rule anyone could undo an event that a verifier holds, a removal among them, by serving a copy of it with one bad entry in `proof`. A verifier that holds more proofs for one event than one record carries, and does not judge them all, treats the log as not verified. The security note that closes core points to this rule.
- **An event dated ahead of its evidence "does not verify" (core 9.5).** The text said "is invalid", which now has a meaning that failure does not have: another verifier's evidence may differ.
- **Evidence for an identity event is evidence of the event with valid proofs (core 9.5).** A verifier records its first sight of an event only once the event has verified. The text already said "with proofs meeting Layer 1, Section 4"; it now says what follows from it. It also says when: as soon as the event verifies for the verifier, with every proof it holds for the event, in however many copies, and with the logs those proofs are judged by. A verifier that waited for one copy to carry enough proofs would count a proof by a removed key that it first saw in between. No vector pins this: the vectors give a verifier its evidence.
- **The logs a verifier must hold (core 9.4)** include the log of a collective under whose threshold a proof is counted, and a member's log as far as the latest evidence among an event and those before it.
- **Entries of `revoked` and `parents` have no other members, and one event revokes at most 80 keys (Layer 1, 3.6, 3.7, 19).** A misspelt `compromisedSince` was ignored in silence, and `revoked` was the one set in an event with no limit.
- **The grammar of an HTTPS origin is the pattern (Layer 1, 3.13).** The text said "a host and an optional port" where both implementations bound the characters only.
- **The DID document of a duplicitous mind says so (Layer 1, 5.2)**, with `duplicitous` in its metadata, and is produced from the state before the divergence.

**The Python checker** also read a `controller` whose value is `null` as absent on a collective's event; it now rejects it, as the schemas do.

**Test vectors.** For the items above (OEP-0002 lists them): 29 negative cases, 29 controls and five must-accept cases. The vectors now hold 22 must-accept cases, 109 negative cases and 59 controls.

**Delegation and Mind Web clarifications ([OEP-0003](../oeps/oep-0003-delegation-and-mind-web-clarifications.md), found while building `@oip/delegation` and `@oip/web`).** No address, content ID or proof in the test vectors changes.

- **A role needs the collective's log, and stops where its members are no longer known (Layer 2, 7.1, item 4; core 9.4).** A member's proof counts for its collective through a charter role only if the verifier holds the collective's log as served no earlier than the evidence for the proof, as for a threshold: a copy older than that may lack the event that removed the member. And it counts only before a duplicitous collective's first conflicting event, from which on nothing is signed for it, under its threshold or through a role.
- **Reserved commands are told by their first segment (Layer 1, 11.2).** `/oipx/pay` is an extension's command.
- **Policy depth (Layer 1, 11.3).** A statement of the policy is at depth 0, and none is deeper than 8. A policy is well formed or not whatever record it is asked of: the statement of a quantifier is part of it where the array is empty too. The reference implementation's evaluator, given a policy that had not been validated, did not look there; it reads a policy whole now.
- **Revocations (Layer 1, 11.5).** A revocation by any mind other than the delegation's author revokes nothing.
- **What a proof is for its signer (Layer 1, 11.6).** A proof whose `authority` is not a valid chain counts for no mind through it and is its signer's own proof all the same. A delegation given inline is judged with the proofs it carries there, and so is a charter (Layer 2, 7.1, item 4); a delegation named and not held leaves the proof not counting for the principal, and a principal's own proof never counts through a chain.
- **`status` (Layer 2, Section 2).** It means something as `withdrawn` or `satisfied` on an Intent and as `withdrawn` on an Offer. A superseding record with any other `status` is neither a withdrawal nor an edit.
- **Copies of a record (Layer 2, Section 2).** Every copy of a record with the same content ID is the same record, of whatever type, and a verifier SHOULD judge it with the proofs of every copy it holds. 5.3 said so for Commitments.
- **An Offer's `quantity` is at least 1 (Layer 2, 4.2).** The text said "integer".
- **Which members of inline objects are required (Layer 2, 2, 4.1, 4.2, 5.1, 6.2).** A budget's `max`, both members of an Offer's price, all four of a Commitment's, a power's `command`, and both members of an assignment and of a link. A budget's `currency` and a role's `purpose` and `powers` are optional, and a power's `policy` defaults to `[]`. The JSON Schemas already had it so.
- **The time of computation of a status (Layer 2, Section 8).** It is compared with `expires` and with a deadline exactly, with no tolerance, and a time "has passed" only after the instant it names. It does not limit which signatures are counted.
- **Which Receipts are superseded (Layer 2, 8.3).** One that another Receipt of the same author names in `supersedes`, if that Receipt is itself a party's and counts for its author. "Later" is not asked.
- **`disputed` (Layer 2, 8.3, item 1).** Every mind's compromise declarations are disregarded for it, not the parties' alone.

Two independent reviews of `@oip/delegation` and `@oip/web` found eight more (OEP-0003, items 17 to 24):

- **The work of a policy is bounded (Layer 1, 11.3 and Section 19, new limit).** Each time a statement is tried on a value counts one, and a comparison by canonical form counts the bytes of the two forms besides. A policy that would count more than 262,144 for a record does not hold for it. The reference implementation stopped at 100,000 evaluations and the Python checker never did, so they disagreed; and neither counted what a comparison costs, so a verifier could be made to work for minutes on one proof.
- **A delegator's log (core 9.4; Layer 1, 11.4).** A proof counts through a delegation chain only if the verifier holds the log of each delegation's author, and of each member of an author that is a collective, as served no earlier than the evidence for the proof. From an older copy it could not judge a revocation it held, and counted the chain.
- **A retired or duplicitous delegator (Layer 1, 11.4, new item 8).** At the proof's time no author of the chain is retired, and none is duplicitous from its first conflicting event on. A mind that can sign nothing can revoke nothing.
- **A revocation stands (Layer 1, 11.5).** Its signature is judged with compromise declarations disregarded, so a mind that declares a key compromised from before one of its own revocations does not give the delegation back.
- **Commands are strings (Layer 1, 11.2).** No segment is normalised.
- **A charter and what replaces it (Layer 2, 6.2; 7.1, item 4).** A charter is completed when first signed, judged with the proofs of every copy held, an inline copy among them; the earlier wording of this proposal judged an inline charter alone. A charter that another names in `supersedes` is in force at no time from that other's completion on. Before, one member could bring back a charter the threshold had replaced.
- **Which Receipt supersedes (Layer 2, 8.3).** One about the same Commitment.
- **No change of text, and a fault in both implementations:** a proof made more than 300 seconds after a record's `expires` does not let its author sign for a party (Layer 2, 5.2 and 7.1).

**Test vectors.** For the items above (OEP-0003 lists them): 33 negative cases, 29 controls and thirteen must-accept cases, among them the items of Layer 1, 11.4 broken one at a time on a two-step chain, and the conditions of a charter role one at a time. The vectors now hold 35 must-accept cases, 142 negative cases and 88 controls. Every value that was there is byte for byte what it was.

**Mind Network clarifications ([OEP-0004](../oeps/oep-0004-mind-network-clarifications.md), found while building `@oip/net`).** The milestone is not finished, and more may follow.

- **A feed that equivocates (Layer 1, 10.3).** A verifier treats the feed as verified up to the entry before the two, and no further.
- **Entries (10.1).** An entry at `seq` 0 has no `prev`. The same entry with other proofs is one entry, judged with the proofs of every copy held.
- **Collectives sign by their threshold (6.1).** Where a clause asks for a valid operational key of a mind, a record signed by a collective under 9.5 meets it. A `Hello` is the exception.
- **An `Ack` may list proofs (13.2; core 9.4, item 4).** `proofs` is an optional array of at most 256 digests of the proofs the packet carried on itself. An `Ack` is evidence for the proofs on the records in the packet's `content` and for the packet's own proofs it lists, and for no other. Before, the text called it evidence for "the sender's proof", which the content ID it names does not cover. This is the one change to a record format.
- **Receiving (12.4).** A packet addressed to a query is rejected if it expires more than one hour after `created`, as 12.1 limits it. A packet addressed by a list is judged by its own proof, whatever `Forwarded` record carries it. The duplicate-detection window is the receiver's to choose, and SHOULD be at least one hour.
- **Sealing (12.6).** A sender does not seal to an agreement key of small order (RFC 9180, 7.1.4), and uses another of the recipient's keys. A recipient rejects a record that opens to anything but the canonical form of a `Packet`.
- **Sessions (14.2 to 14.4).** The first packet of each sending chain carries the `Session` record; a receiver that does not hold the record rejects a packet without it. `to` may list minds that are not participants. A packet has a place in its chain only as a link (`seq` 0 and no `prev`, or a `prev` that is the link before it), and two links at one place are equivocation: so the order packets arrive in decides nothing. A `Resume` that names a packet its receiver's chain does not have there is invalid, and the packet that carries a `Resume` has its place in its sender's chain.
- **Authenticated HTTP requests (13.3).** `alg` may be left out, and is `ed25519` if given. `expires` is later than `created`; a signature made more than 300 seconds before the server's clock has expired. A request has a body when its content is longer than zero bytes, and a server checks a covered `Content-Digest` against the content it received. A signature may cover further components, none with parameters. A request with several signatures is authenticated by the first that meets the profile, and only that one's nonce is seen.

## Revision 2026-11-17 (Draft)

Security and consistency fixes from two independent reviews of revision 2026-10-30, one of the technical paper and one of the specifications, and from a third independent check of those fixes before publication ([reviews/](../reviews/)). Record formats change little; most changes are clearer rules about who may sign what, and when. Every mind address in the test vectors is unchanged.

**Time (core 9).** Time rules use a proof's evaluation time `t(p) = max(p.created, τ(p))`, where `τ(p)` comes from evidence (the verifier's own first-seen record, a witness it trusts, an anchored checkpoint or an acknowledgement), never from the signer's claim. This closes backdating around key removal, compromise, delegation expiry, revocation and collective membership. Evidence belongs to one proof and is keyed by the proof's digest, so evidence that a record existed never covers a co-signature added to it later. Before counting a proof, a verifier holds the signer's log as a trusted witness served it, with the witness's first-seen times, so that the former holder of a removed key cannot outrace the removal. Identity events that remove keys, change membership or retire a mind take effect at their own evaluation time, never earlier than their predecessor's, so they cannot be backdated either; `compromisedSince` is the one deliberately retroactive statement, it reaches back only over the mind's own records, and a commitment it affects shows as `disputed`. A proof made after its record's `expires` does not count.

**Keys (Layer 1, 3 and 6).** One definition of a valid operational key, used everywhere: present at the pinned version, not removed or retired before `t(p)`, not compromised at `t(p)`, the right proof purpose, and, for `Location`, `Participant` and `Hello` only, still current. Feed entries, checkpoints and acknowledgements no longer break when keys rotate. New **invocation keys** (`invocation`) are the only keys a member uses to sign another mind's identity events, so operational keys never change any identity. A member's proof on a collective's identity event counts only if its invocation key had not been removed, nor the member retired, by the event's evaluation time, so a removed invocation key can append nothing; compromise declarations do not reach into other minds' logs, so no member can unmake a collective by disowning old keys. Revoked keys can never be added again. The DID document lists invocation keys under `capabilityInvocation` and uses versioned ids when produced for a `versionId`.

**Thresholds and logs (Layer 1, 3–4).** Thresholds count distinct keys and members and must be majorities (`2t > n`), so duplicity is always attributable. Parameters are validated; every event's type is checked; controllers keep their kind; nothing follows `Retire`; `Merge` and the member name `recovery` are reserved and rejected. A collective's height is fixed by its genesis (an optional `height`, at most 4) and every member must be lower, so a member's later growth can never invalidate the collectives it belongs to, and no collective can contain itself.

**Duplicity (Layer 1, 7).** Duplicity means two events with different content IDs at one position. Branches are never chosen by length or recency: the earlier-evidenced branch wins, otherwise the mind is duplicitous for that verifier, and the removals and compromise declarations of every branch apply to what remains valid. Used control keys must be destroyed; identity events go to at least two witnesses; resolvers record and serve first-seen times, per identity event and per proof.

**Collectives (Layer 1, 9; Layer 2, 6–7).** A collective signs at the earliest time its state's threshold is met by members of that state, with proofs that carry no `authority`; a record describing its present (`Location`, `Participant`) needs the threshold of its latest membership, so members who leave can no longer keep it current. Charter roles use the charter in force at the proof's time, with a tie-break, and a role holder's proof names the charter in its `authority`. A charter is signed by the collective's own authority, and its `expires` bounds only when it can be signed. Recursive threshold signing is reserved. Because invocation keys are reused, a collective's history is verifiable after members rotate them only with evidence of time: verifiers take a collective's event times from witnesses or anchors, resolvers serve them, and collectives should anchor their identity events (Layer 1, 9.6).

**Lineage (Layer 1, 8).** New `Lineage` record: a parent acknowledges a child with an operational key, so routine forks no longer use up a control-key rotation.

**Delegation (Layer 1, 11; Layer 2, 7).** A delegated proof lists, in its own `authority` member and signed with it, exactly the delegations of one chain, root first; verifiers check that list and never search for another, so a proof acts for at most one principal besides its signer, and verification work is linear. A delegation's delegate must differ from its author. Only `Intent`, `Offer`, `Commitment` and `Receipt` can be signed under delegation; `/oip`, `/oip/sign` and `/oip/publish` are reserved (no blanket grants), and `/oip/send` is defined. Policies gain UCAN-style connectives (`not`, `and`, `or`) and quantifiers (`all`, `any`) and array selectors, so a delegation can limit counterparties; ordering operators compare decimals only; a missing member or a malformed value is an error that fails the whole policy, so negation cannot turn it into a pass; amounts are non-negative. Delegators should constrain who pays, the counterparties and the delegate itself, and a policy limit applies per record, not in total. A party bound through a delegate is bound by the structured `terms`. `Delegation.chain` is removed. Nonces have 8–64 characters. Revocations take effect from their evaluation time, and `notBefore` bounds when a proof counts, not when it can be made.

**Layer 2 (5–8).** A Commitment's `price` names its `payer` and `payee`. A Commitment's author must be a party or sign for one through a delegation or a role. Only a commitment that counts for an Intent's or Offer's author can satisfy or exhaust it. A withdrawal has its own status, an edit makes the original `superseded`, and superseding records have a precedence. Each mind appears at most once among a commitment's parties. Status depends on the evaluation time, which is stated.

**Feeds, packets and sessions (Layer 1, 10–15, 18).** Feed entries may commit to the proofs on what they publish, making anchored checkpoints evidence for them; a feed has a single writer; log paging, with first-seen times. Any verb may open a session, and each participant's first packet carries the `Session` record; sending chains are per sender and `instance`; session packets go to every participant and are deduplicated per chain, which also admits packets retransmitted after a `Resume`; `prev` is needed only after a chain's first packet. Packets live at most 7 days; duplicate detection records a packet only after it verifies and keeps it until 300 seconds after `expires`. The `Ack` of a sealed packet names the packet inside. The WebSocket `domain` is set by the client; HTTP signatures have replay rules. Endpoint bindings are defined. Removing the signers of a location record ends it, however high its `seq`. Capability-query packets carry `brokers` and `maxFanout` inside the signed packet, and `Forwarded` names its recipient.

**Bridge (Layer 0).** A gateway attests each mind it bridges with an entry in its own feed naming the mind's genesis, which the mind's profile references; without it the label is only `claimed`. Corrected the A2A Agent Card mapping and digest, Web Bot Auth key identifiers, aliases that cannot point back, and custody handover.

**Core.** Content IDs have one canonical spelling (`^bciq[a-p][a-z2-7]{50}[aiqy]$`) and record-refs match by content ID alone. Ed25519 verification is pinned down: `S < L`, canonical encodings, and keys and `R` of order exactly L, which excludes the identity point and every small-order or mixed-order point (OpenSSL accepts them, so implementations wrap it). Number validity depends on value; decimals are exact and at most 64 characters; timestamps are compared at full precision; string lengths count code points; containers (including `LogPage`) are exempt from the record size limit. Content IDs are not IPFS CIDs. At most 256 proofs per record. New table of every record type.

**Test vectors.** The generator implements the rules above, taking evidence of time from each case. New vectors: a two-step delegation chain, two agents committing for their principals, a packet sent on a principal's behalf, a collective's charter role, a `Lineage` record, a checkpoint, an `Ack`, a `Hello`, DID documents, a bridged mind attested by its gateway, withdrawals and edits, every status of Intents, Offers and Commitments, and the X25519 key. 55 negative cases (each with its reason) must be rejected, 5 must-accept cases accepted, and 11 controls, each a negative case changed only in the respect its reason names, accepted. A second, independent checker written from the first revision's text is in `reviews/spec-review-workfiles/`; it still reproduces the vectors' addresses, content IDs and ordinary signatures, but predates the newer rules (invocation keys, proof-level `authority`, evidence of time), which so far only the generator checks.

**Pre-publication check.** An independent check of the fixes ([reviews/2026-11-17-fix-verification.md](../reviews/2026-11-17-fix-verification.md), of the candidate at commit `ab980a8`) confirmed 37 of the 46 earlier findings resolved and 9 partly resolved, and found ten new issues (N1–N10) and eleven minor ones (M1–M11).
